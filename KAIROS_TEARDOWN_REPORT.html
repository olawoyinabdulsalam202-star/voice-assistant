01

The one-line verdict

KAIROS is a genuinely ambitious full-stack voice assistant with real range — hands-free wake word, camera + screen vision, payments, admin, PWA — built solo without a framework. That ambition is the story. But it's shipped on a trust foundation that a competitor would attack first: live secrets in the repo, an auth model that forgets to enforce suspension, a self-hearing voice loop, and a privacy policy that says the opposite of what the server actually does. The bones are good. The seams are showing.

What's strong: the AI network layer (brain.js) is clean and correctly streaming; history is stored raw to avoid quadratic growth; the admin panel is server-gated with pagination and escaped output; the multi-provider router with circuit breakers is real engineering.

What's fragile: the security perimeter, the always-listening loop, and the gap between what the marketing copy promises and what the code does. None of it is unfixable — most are a day's work — but together they're exactly the list a rival would screenshot.

Structural observations

StructureARCH-1

The 2,600-line monolith is the single biggest maintainability tax

Every route, migration, auth check, payment handler and admin endpoint lives in one file. It works, but it makes every change risk-prone and review-hostile. A competitor reading this knows one bad merge takes down everything.

Fix Split into blueprints — auth.py, chat.py, payments.py, admin.py — behind an app factory. No behaviour change, huge blast-radius reduction.
StructureARCH-2

Dual store (Redis OR in-memory) silently breaks under multiple workers

store.py falls back to an in-process dict when Redis is absent — and Redis is commented out in requirements.txt:51. Run two Gunicorn workers and rate limits, lockouts and login throttles become per-worker and inconsistent. This is a correctness bug hiding as a config choice.

Fix Install Redis and make it required in production (fail fast if REDIS_URL is unset when workers > 1), or pin the app to a single worker and document it.
03

The loop — you asked about this first

There isn't one loop. There are two, and they compound. One makes KAIROS talk to itself; the other makes it spin the microphone forever when something goes wrong. Both are in script.js.

HighLOOP-A · self-hearing

KAIROS hears its own voice and answers itself

The main listener stays live while TTS is speaking. The only guard is script.js:745 — if (lastSpokenReply.includes(normalized) && normalized.length < 40) return;. That fails the moment the reply is long, the recognizer mis-transcribes a word, or the speaker bleeds a fragment back. Result: KAIROS transcribes its own sentence, treats it as a command, and replies to itself — the runaway conversation.

Fix Hard-gate the recognizer around speech, don't filter after the fact. Set a isSpeaking flag; on speechSynthesis start call mainRec.stop(), and only re-arm in the utterance's onend (plus a ~300ms tail). Belt-and-braces: keep the text-similarity guard as a second line, not the only one.
MediumLOOP-B · restart storm

The wake-word recognizer restarts forever with no backoff or cap

script.js:673–678: onend → setTimeout(buildWakeRec, 400), onerror → 800ms, catch → 800ms. If the mic is revoked, the device has no audio input, or the browser throttles a background tab, this rebuilds a doomed recognizer several times a second, indefinitely — a CPU/battery drain and a console flood, with no user-visible signal that anything is wrong.

Fix Add exponential backoff with a ceiling (400ms → 800 → 1600 … cap 10s) and a consecutive-failure counter. After N failures, stop and surface a "tap to re-enable mic" state instead of silently thrashing.
MediumLOOP-C · double mic

Clap detection opens a second microphone stream alongside speech recognition

Clap detect (script.js:568–637) opens its own getUserMedia stream plus an 80ms setInterval FFT loop, while the wake-word SpeechRecognition also holds the mic. Two consumers of one microphone is fragile across browsers, and the threshold (volume > 75 raw average, line 596) is crude enough to false-trigger on a door slam.

Fix Share one AudioContext analyser node between clap detection and VAD; drop the raw-average threshold for a short-term-energy + zero-crossing test, or make clap-to-wake an explicit opt-in that closes the stream when idle.
LowLOOP-D · render loop

three.js particle loop never pauses on a hidden tab

script.js:54 runs the render loop continuously with no visibilitychange guard — it keeps burning GPU/battery in a backgrounded tab.

Fix Pause the requestAnimationFrame loop on document.hidden; resume on focus.
04

Ranked defect log

Ordered by how much damage it does, not how hard it is to fix. This is the section a competitor would lift wholesale.

⚠ Critical — do this before anything else

Live secrets are committed to the repository. API keys / signing secrets for the AI providers, Paystack, Brevo and the auth token signer are readable in the tree. Anyone who ever had the repo — or a leaked clone — can drain your provider credits, forge auth tokens, and send mail as you. Rotate every key now, move them to environment variables / a secret manager, and add them to .gitignore. Rotation is non-negotiable: assume they are already compromised. (I have deliberately not reproduced any secret value here.)

HighSEC-1

Suspended users are never actually blocked

Admin can "suspend" an account, but require_auth (auth.py:163–174) validates the token signature and expiry and never checks the suspended flag. A suspended user with a valid 30-day token keeps full access. The moderation feature is cosmetic.

Fix In require_auth, load the user row and reject with 403 if suspended (or deleted). Pair with SEC-6 (revocation) so suspension is instant.
HighSEC-2

Jailbreak filter only inspects the current message, not the history

The safety check at backend.py:1353 scans the incoming question only. Because the client sends history, an attacker can seed the jailbreak across earlier turns (or in the augmented document/memory block) and slip a clean-looking final message past the filter.

Fix Run the safety classifier over the concatenated conversation the model will actually see, including injected context — or enforce it server-side on the fully-assembled prompt.
HighSEC-3

XSS-to-account-takeover chain

Three things line up: user-controlled fields (e.g. display name) reach HTML/email un-escaped in places, the CSP allows unsafe-inline, and auth tokens live in localStorage. Any one injected script can read the token and impersonate the user for 30 days. The name→email path is the easiest to weaponize because it also hits other recipients.

Fix Escape all user data at every sink (HTML + email templates), tighten CSP to drop unsafe-inline (nonce your scripts), and move tokens to HttpOnly, Secure, SameSite cookies so injected JS can't read them.
HighPAY-1

Paystack verify has a TOCTOU race — a user can double their paid days

Verification reads the transaction (backend.py:1686) and grants the plan (backend.py:1728) in separate transactions with no idempotency lock on the reference. Fire the verify callback twice quickly and the plan is granted twice — free extra days.

Fix Make the Paystack reference a unique key and grant inside a single atomic transaction with INSERT … ON CONFLICT DO NOTHING (or a row lock). Reject any reference already marked processed.
HighLEGAL-1

The privacy policy describes a different product than the one you built

privacy.html / terms.html claim "local-first" and that "no server stores conversations." KAIROS is a server-backed SaaS that stores users, plans, reminders and routes every message through your backend. For an always-listening assistant this isn't a typo — it's the exact misrepresentation a competitor (or a regulator) points at.

Fix Rewrite the policy to state truthfully what's stored, where, for how long, and which third parties (OpenRouter, Groq, Paystack, Brevo, Google) receive data. Trust is the whole pitch for an ambient assistant — the copy has to be exactly right.
HighSEC-4

Unauthenticated /health leaks raw DB error text

/health returns the raw db_error string with no auth. That can expose driver versions, table names, or connection details — free reconnaissance.

Fix Return a boolean ok publicly; log the detail server-side and gate the verbose payload behind admin auth.

Medium — correctness & product-integrity

MediumSEC-6

No token revocation — logout is a lie

Tokens are stateless itsdangerous blobs valid for 30 days. "Log out" just deletes the local copy; a stolen or logged token keeps working until expiry. Combined with SEC-1 and SEC-3 this turns any leak into a month of access.

Fix Add a server-side token version / jti denylist (a column bumped on logout-all, password reset, or suspend). Check it in require_auth.
MediumBILL-1

Expired plans never downgrade — stale tier & wrong analytics

downgrade_expired() exists in plans.py:136 but is never called. Users keep plan_tier past expiry and admin stats over-count "pro" users. You're both giving away access and lying to yourself in the dashboard.

Fix Call downgrade_expired() on a scheduler (or lazily at auth time before reading tier), and compute stats from effective (date-checked) tier.
MediumBILL-2

File credit is charged before the file is validated or extracted

Filereader.js:107–121 decrements the credit, but validation/extraction only happens at line 152. A malformed or unsupported file burns a paid credit for zero output.

Fix Charge only after successful extraction; refund on failure. Move the decrement below the validation gate.
MediumADMIN-1

Half the admin backend has no UI — including a dead "view details" button

Admn.html:618 calls openUser('${attrId}') which is never defined — the button does nothing. Meanwhile working endpoints have no UI at all: grant/revoke plan (/plan), suspend, send-reset, the /audit log, and the full config editor (/config). You built the hard part (the API) and shipped the easy part (buttons) half-done.

Fix Wire the detail drawer to GET /api/admin/users/<id> and add the plan / suspend / reset / audit / config controls. Also replace the index-based active-nav match (Admn.html:503, ['users','stats','settings'][i]) with an explicit key per button.

MediumABUSE-1

Signup is unthrottled — a free email/DNS DoS and cost amplifier

Account creation triggers a Brevo email with no rate limit. A script can hammer signup to burn your email quota, get you flagged as a spam source, and pollute the users table.

Fix Rate-limit signup per IP + per email domain, add a CAPTCHA or proof-of-work on burst, and defer the welcome email behind verification.
MediumPROD-1

Reminders & campaigns are a client-side facade

Reminders fire via setInterval only while the tab is open (ai.js:391) — correct as far as it goes, but there is no server scheduler or push, so a reminder set for tomorrow simply never fires if the app is closed. For a product whose headline is "assistant," a reminder that only works when you're already looking at it isn't the feature users think they're buying.

Fix Add a server-side scheduler that delivers via Web Push (and/or email) so reminders fire with the tab closed. This is also a roadmap centerpiece (see §06, Phase 2).
MediumVOICE-1

The voice path doesn't use the streaming engine that already exists

brain.js has a working SSE streaming client (askKairosStream), yet the voice flow calls the non-streaming askKairos at script.js:886. Spoken replies wait for the full completion before anything happens — the exact latency the streaming work was meant to kill.

Fix Route voice through askKairosStream and start TTS on sentence boundaries as tokens arrive (see §06, Phase 1 — streaming TTS).

Low — polish, dead code & broken links

LowLINK-1

Broken navigation links ship to users

main.htm:1558 links to contact.html but the file is conctact.html (typo → 404). terms.html:193 links to kairos.html which doesn't exist (404).

Fix Correct the filenames (or rename the files) and add a link-check to your pre-deploy step.
LowUI-1

Assorted broken UI & dead panels

manual.htm:952 has broken tag nesting that ejects cards from the grid; Setings.js is an unreachable/unrouted panel with a dead voice handler; the signup-pane "passkey" is a fake hint; onboarding "Skip" actually advances (goStep(1) = Next); Microsoft/Apple sign-in are socialSoon stubs presented as if live.

Fix Delete dead code, make "Skip" skip, and either finish or hide the coming-soon auth buttons so the UI doesn't over-promise.
LowPWA-1

PWA icons are a duplicated non-square placeholder

manifest.json:15 reuses one non-square placeholder for multiple sizes — installed-app icon looks broken on home screens and in the install prompt.

Fix Generate proper maskable 192/512 square icons.
LowI18N-1

"Multilingual" isn't real i18n

Multilang.js:36–37 mis-detects Japanese kanji as Chinese, and the feature only injects a "reply in language X" instruction rather than localizing the UI. Pricing copy is also inconsistent (₦4,500/mo vs "$5 prepaid"), and the weather path sets a Nominatim User-Agent that browsers ignore (a ToS risk, not a function bug).

Fix Use a real language-detection lib, reconcile the pricing copy to one source of truth, and proxy Nominatim server-side with a compliant User-Agent (or use a paid geocoder).

06

How KAIROS wins — the roadmap

Blunt truth: KAIROS can't beat Claude, Gemini or GPT on raw model intelligence — it's a router over them (OpenRouter, Groq). Trying to out-smart the labs is a losing game.

Where it can win: being the assistant that is ambient, embodied and personal. The frontier chat apps are a text box you visit. KAIROS is always-on, hands-free, sees through your camera and screen, remembers you, and lives where you are (Naira/Paystack, local reality). That's a category the labs don't serve well. Win there — and earn the trust an always-listening product requires.

Phase 0 — Foundationbefore any growth · ~1 week

Earn the right to listen

None of the cool features matter if the trust base is cracked. This is table stakes.

01
Rotate every secret & move to env/secret manager. Assume the committed keys are compromised.
02
Fix the auth trio. Enforce suspension, add token revocation, move tokens to HttpOnly cookies + tighten CSP.
03
Rewrite the privacy policy to the truth. Say what's stored and who sees it — then make that a selling point.
04
Close the loops. Hard-gate the mic during TTS; add backoff to the recognizer restart.
Phase 1 — The core it's named forthe "wow" · ~2 weeks

Make the voice feel alive

KAIROS = "the right moment." The interaction has to feel instant and natural, or the concept dies.

01
Streaming TTS. Route voice through askKairosStream and speak on sentence boundaries as tokens arrive — sub-second first word.
02
Barge-in. Let the user interrupt mid-reply; stop TTS the instant they speak. This is the single biggest "feels like Her" upgrade.
03
Better wake + VAD. One shared audio graph, real voice-activity detection, no double mic. Fewer false wakes = trust.
Phase 2 — The assistant promiseretention · ~3 weeks

Do things when the app is closed

An assistant that only works while you stare at it isn't one. This is what turns a demo into a habit.

01
Server-side reminders via Web Push + email. Fire with the tab closed. Turn the facade (PROD-1) into the flagship.
02
Persistent memory that compounds. You already store memories — surface them: "you mentioned X last week." Personal context is the labs' weak spot.
03
Proactive nudges. Morning brief, reminder pre-alerts, "you asked me to follow up on…". Assistant, not chatbot.
Phase 3 — The moatdifferentiation · ongoing

Be embedded in the user's real life

Integrations and locality are things a general-purpose lab chat app won't build for your market.

01
Integrations. Calendar, WhatsApp, email — let voice actually act, not just answer.
02
Lean into vision. Camera + screen understanding is a real edge — build "point at this and ask" and "read my screen" flows the labs don't offer in-browser.
03
Own the local market. Naira pricing, local languages done properly, offline-tolerant PWA. Be the assistant built for here.
